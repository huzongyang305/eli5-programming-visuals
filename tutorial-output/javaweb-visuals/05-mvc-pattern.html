🏪 MVC 架构模式

Model-View-Controller：像餐厅一样分工协作

💡 生活类比：餐厅的分工协作

想象一家餐厅，有三个关键角色：

🧑‍🍳 厨房（Model）：负责准备食材、烹饪菜肴，管理所有数据（菜品信息、库存）
📋 菜单/展示台（View）：负责展示菜品图片、价格，让顾客看到最终呈现
🤵 服务员（Controller）：接收顾客点单，告诉厨房做什么，再把菜端给顾客

核心思想：各司其职，互不干扰！厨房不直接面对顾客，服务员不做菜，菜单不烹饪。

🧑‍🍳
Model（模型）
厨房 / 数据库
• 管理数据和业务逻辑
• 连接数据库（JDBC）
• 处理数据增删改查
• 不包含任何显示代码
📋
View（视图）
菜单 / JSP页面
• 负责用户界面展示
• JSP / HTML 页面
• 显示 Model 提供的数据
• 不包含业务逻辑
🤵
Controller（控制器）
服务员 / Servlet
• 接收用户请求
• 调用 Model 处理数据
• 选择 View 展示结果
• 协调 Model 和 View

✨ 详细流程说明
  1. 用户点击"查看商品" → 浏览器发送 HTTP 请求到 Servlet（Controller）
  2. Servlet 接收请求 → 解析参数，决定需要哪些数据
  3. Servlet 调用 Model → 通过 JDBC 从数据库查询商品信息
  4. Model 返回数据 → 把商品列表封装成 Java 对象返回
  5. Servlet 选择 View → 将数据放入 request，转发到 JSP 页面
  6. JSP 渲染页面 → 遍历数据，生成 HTML 展示给用户
// ========== Controller: OrderServlet.java（服务员）==========
public class OrderServlet extends HttpServlet { protected void doGet(HttpServletRequest request, HttpServletResponse response) { // 1. 接收顾客订单 String dishName = request.getParameter("dish"); // 2. 叫厨房做菜（调用 Model） DishService dishService = new DishService(); Dish dish = dishService.findByName(dishName); // 3. 把菜交给传菜员（存入 request） request.setAttribute("dish", dish); // 4. 端到餐桌（转发到 JSP 视图） request.getRequestDispatcher("/dish-detail.jsp").forward(request, response); } }
// ========== Model: DishService.java（厨房）==========
public class DishService { public Dish findByName(String name) { // 连接数据库查询菜品信息 Connection conn = DBUtil.getConnection(); PreparedStatement ps = conn.prepareStatement( "SELECT * FROM dishes WHERE name = ?" ); ps.setString(1, name); ResultSet rs = ps.executeQuery(); if (rs.next()) { Dish dish = new Dish(); dish.setName(rs.getString("name")); dish.setPrice(rs.getDouble("price")); return dish; } return null; } }
<!-- ========== View: dish-detail.jsp（菜单展示）========== -->
<html> <body> <h1>${dish.name}</h1> <p>价格：¥${dish.price}</p> <img src="${dish.imageUrl}" /> </body> </html>
对比维度 ❌ 没有 MVC（混乱） ✅ 使用 MVC（清晰）
代码结构 SQL、HTML、Java 混在一起 各司其职，层次分明
修改界面 要改多处代码，容易出错 只改 JSP，不影响其他层
团队协作 前端后端互相干扰 前端做 View，后端做 Model/Controller
代码复用 相同逻辑到处复制 Model 可被多个 Controller 调用
测试难度 难以单独测试业务逻辑 可单独测试 Model，无需启动服务器
维护成本 牵一发而动全身 修改一层，不影响其他层

🎯 核心要点总结
  • 分离关注点：每层只做自己擅长的事，降低耦合度
  • 提高可维护性：修改界面不用动业务逻辑，修改数据库不用动页面
  • 便于团队协作：前端专注 View，后端专注 Model 和 Controller
  • 增强代码复用：同一个 Model 可被多个 Controller 调用
  • 简化测试：可独立测试每一层，无需启动完整应用
