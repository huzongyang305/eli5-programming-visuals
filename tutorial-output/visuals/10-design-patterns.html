🧩 ELI5: 设计模式是什么？

设计模式 = 前辈程序员总结好的"解题套路"，遇到类似问题直接套用

💡 生活类比：装修房子的"标准做法"

盖房子时，"卫生间要做防水""承重墙不能拆""插座离地 30cm"——这些不是某个人发明的，而是无数房子盖出来后总结的标准套路。你照着做，就能避开前人踩过的坑。

编程里的设计模式就是这样：面对反复出现的设计难题（比如"怎么保证只有一个实例""怎么让一堆对象收到通知"），前人提炼出了可复用的解决方案。你不用每次从零想，直接套模式即可。1994 年"四人帮"(GoF) 整理了 23 种经典模式，分成三大类：

🏭

创建型模式

关注"怎么造对象"。把对象的创建和使用分开，让造对象更灵活。
例：单例、工厂、建造者

🧱

结构型模式

关注"怎么拼装对象"。让类与类组合成更大结构时更省心。
例：适配器、装饰器、代理

🎭

行为型模式

关注"对象之间怎么沟通"。让职责分配和消息传递更清晰。
例：观察者、策略、状态

下面挑 6 个最常用、最好懂的模式，每个都能动手玩 👇

1. 单例模式 (Singleton)
①
创建型

🌍 生活类比

一个公司只有一个 CEO，一个国家只有一个政府。不管你在哪个部门提到"CEO"，指的都是同一个人——绝不会每提一次就新招一个。单例就是保证"某个东西全局只有一个实例"。

🎮 动手玩：反复"获取实例"，看看是不是同一个

还没创建实例。点上面的按钮试试 →
// C++：懒汉式单例（C++11 起线程安全） class Config { public: static Config& instance() { static Config inst; // 只在第一次调用时构造 return inst; } Config(const Config&) = delete; // 禁止拷贝 Config& operator=(const Config&) = delete; private: Config() {} // 构造函数私有，外部无法 new };
// Java：枚举单例（最简洁、天然防反射和序列化破坏） public enum Config { INSTANCE; public void load() { /* ... */ } } // 使用： Config.INSTANCE.load(); // 或者经典的双重检查锁写法： public class Config { private static volatile Config inst; private Config() {} public static Config getInstance() { if (inst == null) { synchronized (Config.class) { if (inst == null) inst = new Config(); } } return inst; } }
2. 工厂模式 (Factory)
🏭
创建型

🍔 生活类比

你去餐厅只说"来一份汉堡"，后厨就把汉堡做好端上来。你不需要知道它怎么煎肉、怎么烤面包。工厂模式就是那个"后厨"：你说要什么，它负责造好给你，把"怎么造"藏起来。

🎮 动手玩：向工厂下单，看它造出什么

工厂待命中。点一杯饮品 →
// C++：简单工厂，根据类型返回对应产品 class Drink { public: virtual ~Drink() {} virtual std::string name() = 0; }; class Coffee : public Drink { public: std::string name() override { return "咖啡"; } }; class Tea : public Drink { public: std::string name() override { return "茶"; } }; class DrinkFactory { public: static std::unique_ptr<Drink> create(const std::string& type) { if (type == "coffee") return std::make_unique<Coffee>(); if (type == "tea") return std::make_unique<Tea>(); return nullptr; } };
// Java：工厂方法，新增产品无需改调用方 interface Drink { String name(); } class Coffee implements Drink { public String name() { return "咖啡"; } } class Tea implements Drink { public String name() { return "茶"; } } class DrinkFactory { static Drink create(String type) { switch (type) { case "coffee": return new Coffee(); case "tea": return new Tea(); default: throw new IllegalArgumentException(type); } } }
3. 观察者模式 (Observer)
📣
行为型

📱 生活类比

你关注了一个公众号（订阅）。博主一发文（发布通知），所有粉丝都自动收到推送——博主不需要一个个记住粉丝是谁、挨个打电话。这就是"一对多"的自动通知。

🎮 动手玩：订阅/退订粉丝，然后发布一条通知

🙋粉丝A 🙋‍♀️粉丝B 🙋‍♂️粉丝C
3 位粉丝已订阅。点"发布新文章"看看谁会收到 →
// C++：主题维护观察者列表，状态变化时逐个通知 class Observer { public: virtual void update(const std::string& msg) = 0; }; class Channel { std::vector<Observer*> subs; public: void subscribe(Observer* o) { subs.push_back(o); } void unsubscribe(Observer* o) { subs.erase(std::remove(subs.begin(), subs.end(), o), subs.end()); } void publish(const std::string& msg) { for (auto* o : subs) o->update(msg); // 一对多广播 } };
// Java：接口 + 列表，发布时遍历通知 interface Observer { void update(String msg); } class Channel { private List<Observer> subs = new ArrayList<>(); public void subscribe(Observer o) { subs.add(o); } public void unsubscribe(Observer o) { subs.remove(o); } public void publish(String msg) { for (Observer o : subs) o.update(msg); // 一对多广播 } }
4. 策略模式 (Strategy)
🧭
行为型

🚗 生活类比

从家到公司，你可以走路、骑车、开车、坐地铁。目的地一样，但"怎么走"是可替换的策略，还能随时换。策略模式就是把"做同一件事的不同方法"各自封装起来，用哪个由你挑。

🎮 动手玩：选一种出行策略，看耗时和花费怎么变

当前策略：走路 → 60 分钟，花费 0 元，碳排放低
// C++：策略即接口，运行时可替换具体实现 class RouteStrategy { public: virtual ~RouteStrategy() {} virtual void go() = 0; }; class Walk : public RouteStrategy { public: void go() override { /* 走路 */ } }; class Bike : public RouteStrategy { public: void go() override { /* 骑车 */ } }; class Navigator { RouteStrategy* strategy; public: void setStrategy(RouteStrategy* s) { strategy = s; } // 随时换策略 void start() { strategy->go(); } };
// Java：用接口封装算法族，Context 持有可替换的策略 interface RouteStrategy { void go(); } class Walk implements RouteStrategy { public void go() { /* 走路 */ } } class Bike implements RouteStrategy { public void go() { /* 骑车 */ } } class Navigator { private RouteStrategy strategy; public void setStrategy(RouteStrategy s) { this.strategy = s; } public void start() { strategy.go(); } // 委托给当前策略 } // Java 里也常用 Lambda 简化： Navigator n = ...; n.setStrategy(() -> System.out.println("骑车"));
5. 装饰器模式 (Decorator)
🎁
结构型

☕ 生活类比

一杯基础咖啡，你可以加奶 +2 元、加糖 +1 元、加一份浓缩 +5 元。每加一样，就在原来的基础上"包一层"，价格和功能层层叠加，但核心还是那杯咖啡。装饰器就是动态地给对象"加料"。

🎮 动手玩：勾选配料，看价格怎么一层层叠上去

基础咖啡 = 10 元
// C++：装饰器持有被装饰对象，接口一致，功能叠加 class Coffee { public: virtual ~Coffee() {} virtual int cost() = 0; }; class SimpleCoffee : public Coffee { public: int cost() override { return 10; } }; class MilkDecorator : public Coffee { Coffee* inner; public: MilkDecorator(Coffee* c) : inner(c) {} int cost() override { return inner->cost() + 2; } // 在原价格上加料 };
// Java：装饰器实现同一接口，包装并增强原对象 interface Coffee { int cost(); } class SimpleCoffee implements Coffee { public int cost() { return 10; } } class MilkDecorator implements Coffee { private final Coffee inner; MilkDecorator(Coffee c) { this.inner = c; } public int cost() { return inner.cost() + 2; } // 层层叠加 } // 使用： new MilkDecorator(new SimpleCoffee()).cost() == 12
6. 适配器模式 (Adapter)
🔌
结构型

✈️ 生活类比

出国旅行，你的充电器插不进当地插座，于是用一个转换插头。它一头接当地插座、一头接你的充电器，让"本来不兼容的两方"能协作。适配器就是把一个接口"翻译"成另一个接口。

🎮 动手玩：不同国家的插座，靠适配器统一供电

插座：国标 → 适配器转换 → ✅ 充电器正常供电
// C++：适配器把旧接口包装成目标接口 class Socket { public: virtual ~Socket() {} virtual void power() = 0; }; class Charger { public: void charge() { /* 需要 CN 接口 */ } }; class SocketAdapter : public Socket { Charger charger; public: void power() override { charger.charge(); } // 把 power() 翻译成 charge() };
// Java：适配器实现目标接口，内部委托给被适配对象 interface Socket { void power(); } class Charger { void charge() { /* 需要 CN 接口 */ } } class SocketAdapter implements Socket { private final Charger charger = new Charger(); public void power() { charger.charge(); } // 接口翻译 }

📊 六大模式速查表

模式类别一句话生活类比
单例 Singleton创建型全局只有一个实例唯一的 CEO
工厂 Factory创建型你说要什么，它负责造餐厅后厨
观察者 Observer行为型一对多自动通知公众号推送
策略 Strategy行为型同一件事的多种做法可替换出行方式
装饰器 Decorator结构型动态给对象加功能咖啡加料
适配器 Adapter结构型把不兼容的接口翻译成兼容转换插头

🎯 用设计模式有什么好处

🗣️

团队共同语言

说"这里用观察者模式"，同事立刻懂你的设计意图，不用长篇解释。

♻️

复用成熟方案

站在前人肩膀上，避免重复造轮子、重复踩坑。

🔧

易扩展易维护

多数模式都在降低耦合，加新功能时改动范围小。

📐

代码更规整

结构清晰、职责分明，新人也更容易读懂。

⚖️ 权衡与提醒

  • 🚫 别为了用而用：模式是工具不是目的。简单问题硬套模式，反而让代码更复杂（过度设计）。
  • 📈 有学习成本：团队不熟悉时，滥用模式会降低可读性。先理解意图，再决定是否引入。
  • 🔍 识别时机：当你发现"同样的代码结构反复出现""加一个功能要改一堆地方"时，往往就是该上模式的信号。
  • 🧩 模式会组合：真实项目里常多个模式一起用（如工厂 + 单例 + 观察者），不必拘泥于单一模式。

🎯 核心要点总结

  • 设计模式是前人总结的可复用"解题套路"，不是具体代码库。
  • 三大类：创建型（怎么造）、结构型（怎么拼）、行为型（怎么沟通）。
  • 单例保证唯一实例，工厂封装创建，观察者做一对多通知。
  • 策略让算法可替换，装饰器动态加功能，适配器做接口翻译。
  • 记住：模式服务于问题，先有痛点再选模式，切忌过度设计！
